# @standfast/db

Postgres 16 schema, migrations and row-level security.

## Migrations are reversible, and that is enforced

`CLAUDE.md` requires every migration to be reversible and tested against an
ephemeral database. `drizzle-kit generate` produces forward-only SQL, so the
reverse half is written by hand and lives beside it:

```
migrations/
  0000_initial_schema.sql        <- generated by drizzle-kit, applied as `up`
  0000_initial_schema.down.sql   <- hand-written, applied as `down`
```

Rules:

- Every `NNNN_*.sql` has a `NNNN_*.down.sql` sibling. CI fails on a missing one.
- The down file undoes the up file exactly — no partial reversals, no
  "we will never roll this back in practice".
- CI runs `up → down → up` against a throwaway `pgvector/pgvector:pg16`
  container. A migration that cannot survive that round trip does not merge.

## Row-level security

RLS is written in the first migration, not retrofitted. Drizzle covers
`pgPolicy` and `enableRLS`; where it does not reach — HNSW index parameters,
`pg_trgm` operator classes, policy expressions using custom GUCs — write raw
SQL in the migration rather than bending the schema definition to fit.

Design principle 2: a tenant-isolation guarantee is only worth something if
there is a test that *attempts* to cross the boundary and watches it fail.
That test is a permanent regression test, not a one-off check.

## Extensions required

`vector` (pgvector, HNSW, 1024 dimensions), `pg_trgm`, and the built-in
`tsvector`. The first migration creates them.
