# Git export

> **Status: implemented.** `standfast export` lives in
> `packages/cli/src/export.ts` and does what this document says: documents
> byte-for-byte, the atom projection, the manifest, the owned-directory
> semantics and the idempotence contract, with `safeJoin` still refusing a
> server-supplied path that escapes the directory. Built in phase 4
> (`docs/14-roadmap.md`).

## Why this exists

`docs/02-principles.md` (11): *anti-lock-in is a feature*. It removes a major
purchase objection for very little engineering.

The objection is not abstract. Standfast asks a team to move the record of its
decisions into a database it does not run, and the first question anyone
competent asks is what happens when they stop paying, when we stop existing, or
when a migration goes wrong. Every answer that begins "you can call the API" is
the wrong answer, because it is still a dependency on us.

The right answer is a directory of Markdown, in the customer's own layout,
readable in a text editor by someone who has never heard of this product, sat
in a repository they control. That answer is only credible if it exists before
anyone asks, which is why a one-shot version shipped in phase 0 rather than
being scheduled.

It is also cheap. The whole of what exists today is `exportAll` and the two
helpers it leans on, and the design below is not much more. A feature this cheap that answers a question
this expensive should not be an item on a roadmap.

## What exists today

`packages/cli/src/export.ts`, `exportAll`. The one-shot version shipped in
phase 0; phase 4 completed it to this document.

```
standfast export [directory]        # default: ./standfast-export
```

It lists projects, lists each project's documents, and writes each `doc.body`
to `<directory>/<project-slug>/<doc.path>`, creating parent directories as it
goes. It reports a count. With `--json` it emits `{ target, written, swept,
exportedAt }`, which matters later — see *Git*.

`safeJoin` (same file) resolves each destination and refuses anything that
lands outside the export directory. `packages/cli/src/cli.test.ts` asserts the
refusals.

The rest of this document says what the export does beyond that — the atom
projection, the manifest, deletion, the idempotence contract — and why each
came out the way it did.

## What is exported

| Thing | Exported | Form |
| --- | --- | --- |
| Documents | yes | the body, byte-for-byte, at the customer's own path |
| Atoms | yes | a Markdown projection file per document |
| Ratification state | yes | status, time and ratifier name, on each atom |
| Sections | as structure | headings and `section_hash` group the atoms |
| `atom_events` | no | see *Considered and declined* |
| Embeddings | no | a vector is a number nobody can read without our model |
| Reconciliation findings | not yet | the tables exist (`0009`); the format is open |
| API keys | no | — |
| Source code | no | none is held (`docs/01-thesis.md`, invariant 3) |

### Why atoms are exported at all

There is a tidy argument for exporting documents only: atoms are a projection
(invariant 1), projections re-derive (principle 7), so exporting them is
exporting a cache.

It is wrong, for one reason. Re-derivation requires Standfast. A customer who has
left, or whose vendor has gone, cannot re-run extraction — and the thing they
would lose is not the extraction, which a future model would redo better
anyway. It is **ratification**. `status`, `ratified_by` and `ratified_at` are
human judgement, the scarcest input in the system and the one principle 5 makes
a first-class metric. Nothing regenerates a year of someone reading a queue.

So the export carries the projection *and* the decisions taken about it. An
export of documents alone would be a backup. An export that also says which
statements a human accepted is the knowledge base.

## The atom projection format

One file per document, mirroring its path, listing the atoms projected from it
in section order. Not one file per atom: thousands of near-empty files produce
unreadable diffs, and they quietly invert invariant 1 by making atoms look like
the source.

```markdown
---
standfast: atoms/v1
project: standfast
document: docs/02-principles.md
document_id: 3f1c9a2e-8d40-4c1b-9a77-6b2f0e5d1c84
---

# Atoms projected from docs/02-principles.md

Generated by `standfast export`. Every statement below is a projection of the
quoted text in the document at the same path. Do not edit this file. Edit the
document.

## Design principles › Determinism on the read path

section 4 · a91f7c2e…

### 0d9c1f2a

**No generative model call sits between an agent's question and its answer.**

- kind: constraint
- status: canonical
- ratified: 2026-07-30 by Jae Quilichini (human)
- span: 812–1004

> No generative model call between an agent's question and its answer: the
> pipeline admits only pinned, bounded embedding and reranking calls, and
> nothing that generates text.
```

Five choices in that, each of which had an alternative.

**The heading is the atom id, not the statement.** A statement is prose and
changes whenever extraction improves; an id does not. Headings that move on
every re-extraction make the git history unreadable, which defeats the point of
putting the export in git. The cost is a less scannable file, paid back by the
bold statement immediately below. The short id is the first eight hex digits;
the full id is recoverable from the API while it exists, and the short form is
what a human types into a search box.

**Sections are headings, and carry their `section_hash`.** The heading path is
joined with `›` for display only. Identity is the hash, for exactly the reason
`packages/core/src/hash.ts` length-prefixes its inputs: no separator is safe
against a heading that contains it, so no separator is ever the identity.

**The quote is a blockquote, and the span is a number.** The quote alone is
verifiable by substring search, and that is enough until a quote appears twice
in one section. The span settles it. Offsets are Unicode code points, not
bytes, because that is what `packages/core/src/markdown.ts` counts — an offline
verifier that assumes bytes will be wrong on any document containing an em
dash, which is every document in this repository.

**Superseded atoms stay, below the active ones, marked.** A record that drops
its own history is not a record. Putting them last keeps the readable part
readable.

**No timestamp anywhere in a tracked file.** See *Idempotence*.

### One prerequisite, met

The `Atom` response schema in `infra/openapi/openapi.json` now serves
everything the projection prints: `source_quote` and `source_span` on every
read, `superseded_by` always present and nullable, and the ratifier's name
and kind on the list route. The OpenAPI diff and SDK regeneration this
paragraph once asked for have happened, gated by CI as any change to the
committed artifact is.

## The layout on disk

```
standfast-export/
  README.md                     what this is, and how to read it without us
  standfast.json                the manifest
  <slug>/                       one directory per project, keyed by slug
    docs/01-thesis.md           the document, byte-for-byte
    docs/02-principles.md
    .standfast/
      atoms/docs/01-thesis.md   its projection, at the same relative path
      atoms/docs/02-principles.md
```

**Documents sit at the customer's own path, at the root of the project
directory.** This is the load-bearing choice, and it buys three things.

It makes the export *diffable against the folder it came from*. `diff -r ./docs
standfast-export/<slug>/docs` is the anti-lock-in claim, checked, by a customer,
in one command. No other layout lets someone verify that nothing was lost.

It makes the project directory usable as it stands: point a static site
generator, a docs tool, or the phase 4 sync daemon at it and it works, because
it is the folder shape those tools already expect. `docs/01-thesis.md` says the
customer's folder is the working surface; an export that reorganises it hands
back something that is not that folder.

And it makes atoms findable from a path without a lookup table. Given
`docs/02-principles.md`, its atoms are at
`.standfast/atoms/docs/02-principles.md` in the same project directory. No index,
no join, no ids to resolve.

`doc.path` is already the right shape for this. `storagePath` in the CLI
computes it relative to the working directory with forward slashes, and refuses
a file outside that directory, precisely so that the export can reproduce it.
The two functions are one design.

**Slug, not project id, for the directory name.** Ids are opaque and this
directory is for people. `projects_org_slug_key` makes slugs unique per org, so
within one export they cannot collide.

**Atoms go under a reserved `.standfast/`.** A parallel `documents/` and `atoms/`
pair at the project root would have been tidier to describe, and it pushes
every document down one level, which forfeits the diffability above. The
reserved directory is the price. A document whose stored path begins with
`.standfast/` is refused at export time with an error naming it, rather than
silently overwritten — a collision that fails loudly is a bug report, and one
that fails quietly is data loss.

### The manifest

```json
{
  "standfast": "export/v1",
  "server": "https://api.standfast.ai",
  "projects": [
    {
      "slug": "standfast",
      "id": "…",
      "atoms": 41,
      "documents": [
        { "path": "docs/01-thesis.md", "id": "…", "content_hash": "9f2b…c41" }
      ]
    }
  ]
}
```

`content_hash` lives here and nowhere else. It is SHA-256 hex of the body as
UTF-8 (`packages/core/src/hash.ts`), which means that as long as the exporter
writes the body verbatim — **no line-ending normalisation, no appended
newline** — `sha256sum` on the exported file reproduces it. A customer can
verify the export against the manifest with a tool that ships with their
operating system. That property is worth more than the convenience of also
stamping the hash into each atom file's front matter, which would put one fact
in two homes and eventually in two states.

## Idempotence, and the directory Standfast owns

**Contract: exporting twice against an unchanged knowledge base produces a
byte-identical tree.** This is what makes `git status` meaningful, and it is
the one property that turns a dump into something worth committing.

Two consequences.

**No `exported_at` in any tracked file.** A timestamp in the manifest
guarantees a diff on every run even when nothing changed, and it duplicates
what `git log` already records perfectly. The export time goes to stdout and to
`--json`, where a script can have it. Version control is the home of "when".

**Deletion is part of export.** A document removed on the server has to
disappear from the tree, or the export lies by omission and every subsequent
`git diff` is missing the most important change. So `standfast export` treats its
target as **owned**: it removes anything under a project directory that it did
not write this run.

That is a destructive operation on a path the user supplied, so it is fenced.
If the target exists and does not contain a `standfast.json` from a previous
export, the command refuses and says why. `standfast export ~` must not be a way
to delete a home directory, and "the user typed it" is not a defence when the
default argument is a bare directory name.

## Round-trip

**Documents: yes, and it is already true.** The export writes bodies verbatim,
so pushing them back reconstructs the same rows with the same `content_hash`.

```sh
cd standfast-export/<slug>
standfast doc push $(find docs -name '*.md') --project <id>
```

From phase 4 the sync daemon is the write path and this becomes simpler still:
point it at `standfast-export/<slug>/` and that directory is the working folder.
This is the whole reason the layout reproduces the customer's paths — a
round-trip that needs a translation step is a migration, not a round-trip.

One loss to record: `title` is not preserved. `doc push` sends
`basename(path)`, and today that is the only title any document has, so nothing
is lost in practice. If a future write path sets a real title, the export must
carry it in the manifest, and this paragraph becomes a bug.

**Atom status and ratification: deliberately not re-importable.** An import
that could write `status: canonical` and `ratified_by` would be a way to mint
canonical atoms by writing a file — available to anything that can write a
file, including an agent. That is invariant 2 defeated by a text editor. The
database refuses it anyway: `(ratified_by, ratified_by_kind) → actors (id,
kind)` with `check (ratified_by_kind = 'human')` means a restored row has to
name a real human actor in the target org. But the point is that the *product*
must not offer the path, not merely that the schema survives it being offered.

**Restoring ratification into the same org is a real need and is not designed
here.** It is disaster recovery, not import: keyed on the atom ids in the
export, belonging to an authenticated operator path rather than to `standfast`,
and refusing when the document's `content_hash` no longer matches — a decision
about a statement is not a decision about a document that has since changed.
See *Open*.

## The path guard, and the bug that produced it

```ts
export function safeJoin(base: string, candidate: string): string {
  const baseResolved = resolve(base);
  const joined = resolve(baseResolved, candidate);
  const rel = relative(baseResolved, joined);
  if (rel === "" || rel.startsWith("..") || rel.startsWith(sep)) {
    throw new Error(
      `Refusing to write outside the export directory: ${candidate}`,
    );
  }
  return joined;
}
```

`doc.path` comes from the server. The client writes it to disk. **A server
should not be able to choose where a client writes**, and that sentence is the
entire justification — it does not require anyone to be malicious.

This was found by a real bug, not by threat modelling. An early `doc push`
stored the absolute local path of the file it pushed. Those paths came back
from the server absolute, and `resolve(base, "/Users/…/docs/x.md")` discards
the base entirely and returns the absolute path: the export wrote outside its
own directory, into whatever layout the pushing machine happened to have. The
guard caught it. The fix was two functions, and both are load-bearing:

- `storagePath` fixed **what we store** — repository-relative, forward slashes,
  refusing a file outside the working directory. It also stopped shipping the
  operator's home directory and username to the server, which was the other
  half of the same bug.
- `safeJoin` fixed **what we trust**. `storagePath` runs in one client, at one
  version, today. The store outlives it. A different client, an older row, a
  restored backup or another member of the org can each put a path in the
  database after `storagePath` has done its job.

This is principle 9 — allowlist, never denylist — applied to a filesystem. The
test is "resolves inside the base", not "does not contain `..`". A denylist on
`..` misses absolute paths, misses `..` arriving percent-decoded from a layer
above, and misses whatever the next encoding turns out to be. The allowlist
form asks the only question that matters and is indifferent to how the answer
was smuggled in.

Two known imperfections, recorded rather than glossed:

- The `..` test is a prefix test, so a top-level document literally named
  `..notes.md` is refused. It fails closed on a name nobody has, which is the
  right direction, and it is written down here so that nobody "fixes" it into a
  `..` + separator test without first thinking about `..\` on Windows.
- `resolve` is lexical. It does not consult the filesystem, so a symlink
  already present inside the export directory is followed. Owned-directory
  semantics reduce the exposure — the tree is one we created — but do not close
  it. See *Open*.

## Git: Standfast writes, you commit

**Standfast never runs `git`.** No `init`, no `add`, no `commit`, no `push`, no
reading `.git/`. It writes a directory. Whether that directory is a repository
is the customer's business.

The obvious objection is that this applies principle 6 too literally.
*Recommender, never actor* was written about fixing code and opening pull
requests; committing to a repository the user explicitly named, in a directory
they chose, is not obviously the same act. The objection is fair and the
distinction is real. It still comes out the same way, for a reason that is not
purity:

**A commit has an author.** It carries an identity, a message, a signature and
a place in a shared history. The moment Standfast produces commits, its output
stops being a diff on disk that someone reviews and becomes a line in a log
that someone is accountable for. The failure mode moves with it: an export that
writes a mangled tree over a good one is an unstaged change you discard; the
same export committed is a bad commit in a history other people pull. And to
sign as the developer we would need the developer's signing key, which is a
sentence that ends the conversation on its own.

So a `--commit` flag is declined. It is three lines of engineering, and that is
exactly the trap: a flag that exists gets wired into CI, and then Standfast is
committing to a customer repository on a schedule with nobody reading the
result. A team that wants that should build it, because then it is theirs:

```sh
standfast export ./knowledge --json > /tmp/standfast-export.json
git -C ./knowledge add -A
git -C ./knowledge commit -m "standfast export" || true   # no-op when clean
```

Their CI, their identity, their signing key, their commit. The `--json` output
already tells the script what happened, which is the shape principle 6 asks
for: the system produces and reports; a human or their automation acts.

Pushing to a remote is declined harder, and permanently. It would require
Standfast to hold a write credential to a customer repository — the largest blast
radius anywhere in the product — in service of a feature whose entire purpose
is that the customer does not depend on us.

What we do instead is make the tree pleasant to commit: deterministic ordering,
stable file names, no volatile timestamps, verbatim bodies, and deletion
handled so `git status` tells the truth. Those are the properties that make a
commit worth making. They are also, not coincidentally, the properties that
make the export testable.

## How this is checked

Statements a machine can check, in the spirit of `docs/14-roadmap.md`. All six
run as integration tests in `packages/api/src/cli.integration.test.ts`, and
the path refusals, the atom ordering and the ownership sentinel have units in
`packages/cli/src/cli.test.ts`.

1. Two consecutive exports against an unchanged fixture produce byte-identical
   trees. Idempotence is a gate, not an aspiration.
2. For every exported document, `sha256` of the file equals `content_hash` in
   the manifest. This is the verbatim-body rule, enforced.
3. Every atom in the fixture appears exactly once, in exactly one projection
   file, and every `source_quote` in that file is a substring of the exported
   document at the span given.
4. Export, delete a document server-side, export again: the file is gone from
   the tree.
5. A server response naming `../x`, `/etc/passwd`, or `.standfast/atoms/x.md` is
   refused, not written.
6. Export, then push every document back into an empty project: the resulting
   `content_hash` set is identical.

## Considered and declined

Recorded so each question is asked once.

- **Documents only, no atoms.** Loses ratification, which does not regenerate.
- **One file per atom.** Unreadable diffs, and it makes the projection look
  like the source.
- **A separate JSON dump alongside the Markdown.** Two representations of one
  set of facts, drifting quietly — the same argument that rejected a
  hand-written SDK in `docs/03-architecture.md`. The Markdown *is* the
  machine-readable form: the front matter and the field bullets parse.
- **`documents/` and `atoms/` as sibling trees.** Tidier to explain, and it
  pushes every document one level down, forfeiting `diff -r` against the
  original folder.
- **Project id as the directory name.** Opaque, and slugs are already unique
  per org.
- **`exported_at` in the manifest.** Guarantees a diff on every run, and
  duplicates `git log`.
- **`--commit` and `--push`.** See *Git*.
- **Exporting `atom_events`.** The decision that stuck is already on the atom
  row. The full log is an audit view (phase 5), it is the largest table in the
  system, and rendering an append-only log as Markdown produces a file whose
  diff grows without ever becoming readable. If it is ever exported it belongs
  in JSONL next to the manifest, not in the projection files.
- **Exporting embeddings.** Model-version-specific floats, useless outside the
  model that produced them. Phase 1 has shipped, so the question is live rather
  than hypothetical, and the answer has not changed.
- **An `export` MCP tool.** Already declined in `docs/08-mcp-server.md`: it is
  a human operation, not something an agent does mid-task, and its description
  would spend session tokens in every session to describe a command nobody
  calls from one.

## Open

- **Restoring ratification into the same org.** Wanted, not designed. The
  constraints are known — keyed on atom ids, operator-authenticated, refusing
  on a `content_hash` mismatch, never a path an agent can reach — but the
  surface is not chosen and no phase owns it yet.
- **Symlink and platform gaps in `safeJoin`.** `resolve` is lexical, so a
  symlink inside the target is followed; whether the fix is `realpath` per
  component, `O_NOFOLLOW`, or simply refusing a target we did not create, is
  undecided. Two related cases are unverified because CI runs Linux and macOS
  only: a Windows path naming a different drive (`D:\…`), where `relative`
  returns the path unchanged so neither test fires, and case-insensitive
  filesystems, where two distinct `doc.path` values can collide on disk.
- **Reconciliation findings.** They are verdicts and `path:line` pointers about
  the customer's own code, and a customer leaving should take them with them.
  The tables exist — `reconciliation_runs` and `reconciliation_findings`,
  migration `0009` — and the format does not. One constraint is fixed in
  advance: no field of it carries source.
- **Scale.** The current export is a paged walk of the projects plus a paged
  walk of each project's documents — `pageAll` in `packages/cli/src/commands.ts`
  follows every page — holding each body in memory before writing it. Nobody
  has run it against a corpus large enough to know where it stops being fine,
  and inventing a number here would be inventing a benchmark.
- **Whether an export should be signed**, so a customer can prove a tree came
  from their Standfast. Principle 12 covers the release supply chain, not exported
  data, and there is no consumer for such a signature today.
